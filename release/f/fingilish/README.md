# Fingilish Keyboard — Project README

## Project overview

**Fingilish** is a phonetic Persian keyboard that lets users type Persian using Latin-script transliteration. The user types a full Latin word; on a word boundary (space or enter) it is converted to Persian script.

Example:
- type `salam`, press space → `سلام `
- type `mitooni` + space → `میتونی `
- type `kheili` + space → `خیلی `

The project has two halves:

1. **The Keyman keyboard + lexical model** — the conversion engine, dictionary, and suggestion banner, built on the Keyman platform
2. **A standalone iOS app** — a polished App Store keyboard extension embedding KeymanEngine, with no dependency on the Keyman app

The original first-milestone behavior (`in` → `این`, `ye` → `یه`, `oon` → `اون`, etc.) has long been achieved. The project is now in **TestFlight beta**, with **build 1.0 (3) uploaded to App Store Connect**.

## Architecture

The keyboard is a **hybrid IME**, replacing the earlier approach of 500+ individual `.kmn` word rules. Three layers:

### Layer 1 — `fingilish.kmn` (keyboard, "Phonetic Persian", v1.1)

A minimal Latin pass-through keyboard. Letters, numbers, and symbols output as-is, so the user sees Latin text while typing. On **space and enter**, a rule fires `call(fnConvert)`:

```
store(fnConvert) "fingilish.dll:ConvertWord"
+ [K_SPACE] > call(fnConvert)
+ [K_ENTER] > call(fnConvert)
```

Punctuation keys are currently plain pass-through — they do **not** trigger conversion yet, although the conversion engine already contains trigger-char detection for them (see Layer 2). Wiring punctuation triggers is pending work.

On web/mobile platforms the DLL name is ignored and Keyman invokes the embedded JavaScript in `ConvertWord.call_js` (the IMX mechanism, same pattern the CJK keyboards use).

### Layer 2 — `ConvertWord.call_js` (conversion engine, generated)

The JavaScript engine embedded in the compiled keyboard. **Do not edit by hand** — it is generated by `build_calljs.py` from a template plus `fingilish_dict.json`.

Pipeline on each trigger keypress:

1. Determine the trigger character from `keyEvt.Lcode` (space, enter; the code also recognizes `.`, `,`, `؟`, `!`, `;`, `:` for when punctuation triggers are added to the `.kmn`)
2. Read the trailing Latin word from `target.getTextBeforeCaret()`
3. Look up: **exact key** → **`norm()`-collapsed key** → **algorithmic transliteration fallback**
4. `deleteCharsBeforeCaret(wordLen)`, then insert Persian + the trigger character

The embedded dictionary currently has **28,037 entries** — how users actually type Fingilish (with vowels), not consonant skeletons — built from three sources in priority order: a hand-verified MANUAL dict, a NAMES dict of Persian proper names, and auto-generated transliterations of the frequency wordlist.

**`norm()` — variant collapse.** One canonical implementation, kept in sync in three places (`build_dict.py`, `ConvertWord.call_js`, and `searchTermToKey` in the model):

- Consonants: `x`→`kh`, `q`→`gh`, `w`→`v`, `ph`→`f`
- Long vowels: `aa`→`a`, `oo`→`o`, `ee`→`i`, `ou`→`o`
- `u`→`o` (so `khub` ≡ `khob`), `ey`/`ei`→`i` (so `kheyli` ≡ `khili`)
- Collapse doubled letters

**Algorithmic fallback** for unknown words (names, novel words): longest-match digraphs first (`sh` ش, `ch` چ, `zh` ژ, `kh` خ, `gh` غ, `th` ث), single-consonant map, and context-dependent vowel rules (word-initial `a`/`e` → alef; mid-word short vowels dropped; final `e` → ه; word-initial `o` → او, `i` → ای; etc.). Double consonants are collapsed before transliterating (`mattin` → `matin`).

### Layer 3 — `mattin.fa.fingilish.model.ts` (lexical model, trie-1.0)

Drives the mobile suggestion banner with ranked alternatives. The wordlist (`fingilish.wordlist.tsv`, ~22,500 Persian entries with frequencies) contains Persian words; `searchTermToKey` converts both wordlist entries and typed Latin to a shared normalized key so the trie matches across scripts.

Two hard-won constraints baked into the model:

- **Everything lives inside `searchTermToKey`.** `kmc` compiles the model in a sandboxed scope; top-level module functions are inaccessible at runtime, so all helpers (including a large MANUAL Persian→Latin override table for high-frequency function words and verbs) are defined inside the function.
- **RTL banner fix** (see `RTL_Banner_Fix.md`): `isRTL: true` is set on the model, and every Persian word in the wordlist is wrapped in BiDi isolation characters (U+2067 RLI … U+2069 PDI) by `wrap_bidi.py`. `searchTermToKey` strips `[\u2066-\u2069]` before processing. This forces correct RTL rendering even though the banner inherits LTR direction from the keyboard's `&kmw_rtl` flag. (An upstream Keyman issue for this LTR-keyboard/RTL-model gap still needs to be filed.)

## Build pipeline

**Order matters.** `wrap_bidi.py` modifies the wordlist in place; running `build_dict.py` after it silently rejects every BiDi-wrapped entry and collapses the dictionary from ~28,000 to ~674 entries.

```bash
cd source/words
python build_dict.py        # fingilish_dict.json
python build_calljs.py      # ConvertWord.call_js
python build_lexicon.py     # fingilish.wordlist.tsv
python wrap_bidi.py         # BiDi-wrap the wordlist (LAST — idempotent)
cd ../..
kmc build source/fingilish.kmn --out-file build/fingilish.js
kmc build source/mattin.fa.fingilish.model.ts --out-file build/mattin.fa.fingilish.model.js
kmc build source/fingilish.kps
kmc build source/mattin.fa.fingilish.model.kps
```

To add or fix a word: edit the `MANUAL` dict in `build_dict.py`, re-run the pipeline, rebuild the `.kmp`s, copy into `FingilishApp/Keyboards/`, and **bump the install flag** in `KeyboardViewController.swift` so devices re-extract the resources.

## iOS app specifics

The extension (`SWKeyboard/KeyboardViewController.swift`) does four jobs:

1. **Resource install** — on first launch per install-flag version, extracts the bundled `.kmp`s into the App Group container
2. **fa/EN toggle** — a native pill overlay on the banner that switches between Persian conversion and Latin pass-through (persisted via `fingilish_conversion_on` in the App Group)
3. **Top bar image** — portrait/landscape banner artwork
4. **Post-lock black screen recovery** — the largest chunk of the file (see below)

### The post-lock black screen bug (fixed in build 3)

Locking the iPhone while the keyboard is open kills the WKWebView WebContent process. WebKit silently respawns it and reloads the page, but the remote layer compositing connection to the window server goes stale — the keyboard renders **completely black** while the JS engine reports healthy. No JS-layer probe can detect this.

The shipped fix:

- **All recovery state is process-level `static`** (`everSawHealthy`, `failStreak`, `renderFailStreak`, `failWindow`, `okStreak`, `lastRecovery`, health timer, etc.) — iOS churns `KeyboardViewController` instances on unlock and zeroes instance state
- **Timer-gap detection** identifies unlock events (frozen timers resume with a gap); `NSExtensionHost` notifications fire unreliably
- **Dual-probe render check**: `drawHierarchy` (false-negatives in the broken state) plus `takeSnapshot` (reliably detects black); a hung `takeSnapshot` callback is treated as a black verdict via a 1.5 s watchdog
- **On confirmed black**: `advanceToNextInputMode()` for an instant globe-switch, then `exit(0)` after 0.4 s so returning to Fingilish spawns a fresh working process

### Build/deploy gotchas (learned the hard way)

- Keyboard extensions can't embed their own frameworks — everything lives in the container app's `Frameworks/` with `@executable_path/../../Frameworks` runpath in the extension
- Carthage xcframeworks rebuilt from source on macOS Tahoe must be re-signed with the Apple Distribution cert before upload
- Bump `CFBundleVersion` in **both** `KMSample2/Info.plist` and `SWKeyboard/Info.plist`
- Run `xattr -cr .` immediately before **each** `xcodebuild` (files keep reacquiring extended attributes that break codesign)
- KeymanEngine 19.0 **alpha** is required because stable 18.x doesn't compile under Xcode 26 / Swift 6.2.4; older API dialect applies in places (`RunLoop.main.add(t, forMode: .commonModes)`, `view.bringSubview(toFront:)`)
- `UIApplicationOpenSettingsURLString` (the global) is required on the iOS 26 SDK; `UIApplication.openSettingsURLString` no longer exists as a Swift member
- Device install/log workflow: `devicectl` for installs (its provisioning warning is benign), `pymobiledevice3` for syslog streaming (the stream dies silently on device lock — restart and verify after every lock/unlock)

## One-sentence summary

Fingilish is a **Keyman-based Fingilish→Persian phonetic keyboard shipped as a standalone iOS app** — a Latin pass-through `.kmn` that triggers a generated 28k-entry JavaScript conversion engine on word boundaries, plus a BiDi-fixed trie lexical model for suggestions — currently in **TestFlight beta with build 3 uploaded to App Store Connect**, with punctuation triggers/Persian comma, boilerplate cleanup, and the final App Store submission remaining.
