# Fingilish Keyboard — Project README

## Project overview

**Fingilish** is a phonetic Persian keyboard that lets users type Persian using Latin-script transliteration. The user types a full Latin word; on a word boundary (space, enter, or punctuation) it is converted to Persian script.

Example:
- type `salam`, press space → `سلام `
- type `mitooni` + space → `میتونی `
- `kardi`, `kardy`, and `karde` all resolve → `کردی`

The project has two halves:

1. **The Keyman keyboard + lexical model** (this repo) — the conversion engine, dictionary, and suggestion banner, built on the Keyman platform
2. **A standalone iOS app** (`~/Documents/fingilish/FingilishApp/`, separate git repo) — an App Store keyboard extension embedding KeymanEngine, with no dependency on the Keyman app

Status: **TestFlight beta.** Version 1.0, build 4 archived and uploaded 2026-07-07; Info.plists pre-bumped to build 5 for the next iteration. **This repo is the single source of truth** for all keyboard sources as of 2026-07-07 (previously some shipping files lived only on the Desktop, uncommitted).

## Architecture

The keyboard is a **hybrid IME** — a Latin pass-through keyboard plus a generated JavaScript conversion engine plus a lexical model. Three layers, plus a twin keyboard for the English toggle:

### Layer 1 — `fingilish.kmn` (keyboard, "Fingilish", v1.1)

A minimal Latin pass-through keyboard. Letters, numbers, and symbols output as-is, so the user sees Latin text while typing. Conversion fires on **space, enter, and punctuation**:

```
store(fnConvert) "fingilish.dll:ConvertWord"
+ [K_SPACE] > call(fnConvert)
+ [K_ENTER] > call(fnConvert)
+ [K_PERIOD] > call(fnConvert)         c .
+ [K_COMMA] > call(fnConvert)          c ,
+ [SHIFT K_SLASH] > call(fnConvert)    c ? (inserted as Persian ؟)
+ [SHIFT K_1] > call(fnConvert)        c !
+ [K_COLON] > call(fnConvert)          c ;
+ [SHIFT K_COLON] > call(fnConvert)    c :
```

On web/mobile platforms the DLL name is ignored and Keyman invokes the embedded JavaScript in `ConvertWord.call_js` (the IMX mechanism, same pattern the CJK keyboards use).

**`fingilishlatin.kmn`** ("English", v1.1) is a pure pass-through twin with no conversion rules. The iOS app's **fa/EN toggle** switches between the two keyboards (`fingilish`/`fa` ↔ `fingilishlatin`/`en`); both are packaged in the same `fingilish.kps`.

### Layer 2 — `ConvertWord.call_js` (conversion engine, generated)

The JavaScript engine embedded in the compiled keyboard. **Do not edit by hand** — regenerated by `build_calljs.py` from a template plus `fingilish_dict.json`.

On each trigger keypress:

1. Determine the trigger character from `keyEvt.Lcode` (space, `.`, `,`, `؟` for `?`, `!`, `;`, `:`, newline)
2. Read the trailing Latin word from `target.getTextBeforeCaret()`
3. **Four-tier lookup**: exact key → `norm()`-collapsed key → `skel()` vowel-skeleton key → algorithmic transliteration fallback
4. `deleteCharsBeforeCaret(wordLen)`, insert Persian + trigger character

The dictionary has **28,041 exact entries** (keys are how users actually type Fingilish, with vowels) plus a **16,529-entry skeleton bank**. The skeleton tier exists because auto-generated Persian→Latin keys drop unwritten short vowels (کردی auto-keys as `krdi`, but typists write `kardi`); vowel-stripping both sides rescues that entire class of lookups. Sources in priority order: hand-verified MANUAL dict (incl. the کرد verb family), NAMES dict, auto-transliterated frequency wordlist. Dict format: `{"exact": {...}, "skel": {...}}`.

**`norm()` — variant collapse.** One canonical rule set, kept in sync in three places (`build_dict.py`, the `build_calljs.py` template, and `searchTermToKey` in the model):

- `c`→`s` before e/i/y (`cinema`→`sinema`), else `c`→`k`; `ch` protected as a digraph
- Word-final consonant+`y` → `i` (`kardy`→`kardi`); `eh$`→`e`
- Consonants: `x`→`kh`, `q`→`gh`, `w`→`v`, `ph`→`f`
- Long vowels: `aa`→`a`, `oo`→`o`, `ee`→`i`, `ou`→`o`; `u`→`o` (`khub` ≡ `khob`); `ei`/`ey`→`i` (`kheyli` ≡ `khili`)
- Collapse doubled letters

**Algorithmic fallback** for unknown words: longest-match digraphs first (`sh` ش, `ch` چ, `zh` ژ, `kh` خ, `gh` غ, `th` ث), single-consonant map, context-dependent vowels (single `a`→ا always, word-initial `aa`→آ, mid-word `oo`→و, `ee`→ی, final `e`→ه, apostrophe → ع/ء).

### Layer 3 — `mattin.fa.fingilish.model.ts` (lexical model, trie-1.0)

Drives the mobile suggestion banner with ranked alternatives from `fingilish.wordlist.tsv` (~22,500 Persian entries with frequencies). `searchTermToKey` converts both wordlist entries and typed Latin to a shared normalized key — its rules **must match `norm()`** in the other two locations.

Hard-won constraints baked in:

- **Everything lives inside `searchTermToKey`** — `kmc` compiles the model in a sandboxed scope, so all helpers (including the MANUAL Persian→Latin override table) are defined inside the function
- **RTL banner fix** (see `RTL_Banner_Fix.md`): `isRTL: true` plus BiDi isolation characters (U+2067 RLI … U+2069 PDI) wrapped around every wordlist entry by `wrap_bidi.py`; `searchTermToKey` strips `[\u2066-\u2069]` before processing. (Upstream Keyman issue for the LTR-keyboard/RTL-model banner gap still needs to be filed.)

## Build

```bash
./build.sh              # rebuild engine + keyboards + model packages
./build.sh --lexicon    # also regenerate the wordlist from raw CSVs first
```

`build.sh` encodes two ordering rules that previously caused silent disasters:

1. **Wordlist BiDi-wrapping order**: the wordlist must be wrapped only after `build_lexicon.py`. (`build_dict.py` itself has been order-safe since 2026-07-07 — it strips BiDi isolates on read, so the old trap where running it after `wrap_bidi.py` collapsed the dictionary from ~28k to ~674 entries is dead.)
2. **kvk collision**: both `.kmn` files declare `VISUALKEYBOARD 'fingilish.kvks'`, so each compile emits a `source/fingilish.kvk`. `fingilish`'s artifacts must be staged into `build/` **before** compiling `fingilishlatin`, whose stray kvk is discarded. The `.kps` packages from `../build/`.

To add or fix a word: edit `MANUAL` in `build_dict.py`, run `./build.sh`, then deploy:

```bash
cp build/*.kmp ~/Documents/fingilish/FingilishApp/Keyboards/
# then bump installFlag version in SWKeyboard/KeyboardViewController.swift
```

## iOS app specifics

`~/Documents/fingilish/FingilishApp/` (own git repo). Bundle IDs `com.mattin.fingilish` / `.SystemKeyboard`; App Group `group.com.mattin.fingilish`; Team `65Y4G5T866`. Scheme `KMSample2`; KeymanEngine **19.0 alpha** xcframework (stable 18.x doesn't compile under Xcode 26 / Swift 6.2.4). Current install flag: `fingilish_resources_installed_v1.8` — bump on every `.kmp` change (independent of the `.kmn` `KEYBOARDVERSION`, still '1.1').

The extension (`SWKeyboard/KeyboardViewController.swift`, ~650 lines):

1. **Resource install** — extracts bundled `.kmp`s into the App Group container, once per install-flag version
2. **fa/EN toggle pill** — switches between the `fingilish` and `fingilishlatin` keyboards, persisted via `fingilish_conversion_on`. Beware: `Manager.setKeyboard` can **permanently deregister** a keyboard on certain failures; the toggle code detects and re-registers
3. **System-keyboard metrics match** — native height-constraint adjustment plus injected JS (`setBannerHeight(48)`) to fix the ~19pt-too-tall panel from the oversized banner
4. **Blank-keyboard recovery** — see below

The container app (`KMSample2/ViewController.swift`, ~410 lines) is the onboarding: setup card with numbered steps + "Open Settings" (auto-detects when the keyboard gets enabled and swaps to a ✅ success card with an "Open Messages and try it" deep link), a typing-guide card (digraphs, vowels, apostrophe→ع, flexible spelling, toggle, triggers), a try-it-here text field with its own in-app snapshot-probe recovery, and a no-Full-Access privacy note.

### The post-lock black screen bug (fixed)

Locking the device with the keyboard open kills the WKWebView WebContent process. WebKit respawns it and reloads the page — JS-healthy — but the remote layer compositing connection to the window server is stale, so the extension composites **solid black** (verified via device logs: probe JS succeeds against the new WebContent PID while the screen is black). KeymanEngine ≤19.0 alpha has no handling (upstream keymanapp/keyman#6191).

- **All recovery state is process-level `static`** — iOS churns `KeyboardViewController` instances across lock/unlock while the engine's webview is one shared object; per-instance state never accumulated streaks
- **Two detection layers**: a 2s JS probe (dead/unloaded pages, zero-size OSK) and a native `takeSnapshot` render probe armed for ~10 ticks after each host resume (a rendered keyboard always has pixel contrast; a detached layer snapshots uniform). A hung snapshot callback counts as a black verdict via watchdog
- **Remediation ladder**: engine `reload()` twice, then `exit(0)` — iOS relaunches keyboard extensions on demand and a fresh launch is the known-good state

### Build/deploy gotchas (learned the hard way)

- Keyboard extensions can't embed frameworks — all xcframeworks live in the container app's `Frameworks/` with `@executable_path/../../Frameworks` runpath in the extension
- Carthage xcframeworks rebuilt from source must be re-signed with the Apple Distribution cert before upload (ITMS-91065)
- Bump `CFBundleVersion` in **both** Info.plists; `ITSAppUsesNonExemptEncryption=false` is set
- `xattr -cr .` immediately before every `xcodebuild`
- iOS 26 SDK: `UIApplicationOpenSettingsURLString` global (the Swift member name is gone); engine-era dialect: `RunLoop.main.add(t, forMode: .commonModes)`, `view.bringSubview(toFront:)`
- `devicectl` for installs (provisioning warning benign); `pymobiledevice3` for syslog (stream dies silently on device lock — restart after every lock/unlock)
- KeymanEngine dSYM warning on upload is expected (framework built without dSYM); upload still succeeds
